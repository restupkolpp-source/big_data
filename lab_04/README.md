# Лабораторная работа 4

Взял карточки ДТП за 2025 год из предыдущих работ и обучил модель вероятности погибших
по условиям уже произошедшей аварии. Для признаков использовал время, координаты,
регион, погоду, освещение и число машин. Данные о погибших и раненых в признаки не включал.

Сравнил обычные модели и GaussianNB с дифференциальной приватностью, настроил Feast,
MLflow и REST-инференс. Отдельно разобрал прогноз температуры и предупреждение об аварии на ряде NAB.

Вся реализация находится в одном ноутбуке: функции стоят перед примерами их использования.
Графики и результаты оставил там же, а скриншоты MLflow — в [evidence](evidence/).

## Запуск

Из корня `big_data`, Python 3.13:

```powershell
python -m venv _work/lab04-venv
_work/lab04-venv/Scripts/Activate.ps1
python -m pip install -r lab_04/requirements.txt
python -m nbconvert --execute --to notebook --inplace 'lab_04/Лабораторная работа 4.ipynb' --ExecutePreprocessor.timeout=600
```

Точные версии моего окружения сохранены в `requirements-lock.txt`. Для Windows можно
установить их вместо `requirements.txt`. Файл включает `pywin32`; для Linux нужен основной список.

Карточки читаю из `data/clean/accidents/year=2025/part.parquet`. Если данные лежат в другом месте:

```powershell
$env:DTP_DATA_DIR='C:/путь/к/данным'
```

Подходит тот же каталог `data`, что в ЛР-3. Если выгрузки ещё нет, её можно собрать загрузчиком ЛР-1:

```powershell
python -m pip install -r requirements.txt
python scripts/download_dataset.py --from 2025-01 --to 2025-12 --regions 1132,1140,1145
```

Ряд NAB скачивается при первом запуске. Для него нужен доступ к GitHub.
Результаты, модели, Feature Store и база MLflow лежат в `_work/lab04/`.

## Что проверяю

- Обучение на январе–августе, выбор модели на сентябре–октябре, итоговая оценка на ноябре–декабре.
- Совпадение исторических и online-признаков Feast, отсутствие признаков до появления карточки.
- Логирование моделей и метрик в MLflow, регистрация версии и загрузка через alias `production`.
- REST-инференс с Feast, 200 HTTP-запросов, p50/p95/p99, throughput и ошибки.
- Canary 5%, shadow и возврат предыдущей модели при ухудшении PR-AUC.
- PSI, KS, пропуски, диапазоны, изменение предсказаний и падение качества.
- Доставка алерта на локальный webhook и обучение новой модели по доступным меткам.
- Ежедневное пакетное переобучение и River на одном временном test, прогноз до обновления по метке.
- GaussianNB с epsilon=1 и epsilon=2, общий бюджет двух публикаций epsilon=3, delta=0.
- Прямой и рекурсивный прогноз температуры на 24 ч, q0.9, CUSUM, persistence и cooldown.

Для приватности заранее задал границы признаков [0,1] и классы 0/1.
Гарантия относится к двум приватным моделям и одной карточке ДТП; она не распространяется
на весь эксперимент, обычные модели или опубликованные исходные данные.
Приватные модели обучаю без фиксированного seed, поэтому их результаты меняются при перезапуске.
Повторная публикация расходует дополнительный бюджет.

## MLflow

После выполнения ноутбука:

```powershell
python -m mlflow ui --backend-store-uri sqlite:///_work/lab04/mlflow.db --host 127.0.0.1 --port 5004
```

Открываю [MLflow](http://127.0.0.1:5004), эксперимент `dtp-severity` и модель `DTPSeverity`.
В Registry использую aliases `candidate` и `production`.

REST-сервис можно запустить отдельно после ноутбука:

```powershell
python scripts/run_notebook.py 4 api --port 8044
```

Проверка готовности — [health](http://127.0.0.1:8044/health), описание запросов — [docs](http://127.0.0.1:8044/docs).
`POST /predict` принимает `accident_id` из подготовленного набора и произвольный `request_id`.
После проверки останавливаю сервис и MLflow через Ctrl+C.

## Что получилось

Для редкого исхода смотрю прежде всего PR-AUC. При пороге 0.5 модель может не выдавать
положительных решений, хотя ранжирование лучше константного baseline.
Полный HTTP-запрос включает чтение Feast; его время показываю отдельно от чистого инференса.
В сохранённом прогоне p95 модели — 6.09 мс, полного HTTP-запроса при четырёх клиентах —
83.84 мс, throughput — около 74 запросов/с. Замеры чистой модели и сервиса под нагрузкой показываю отдельно.

В температурном ряде есть многодневные разрывы. Не заполняю их будущими значениями:
сравниваю прогнозы только на полных окнах и сбрасываю состояние детектора после разрыва.
Параметры предупреждения выбираю по первой аварии и цене ошибок, затем фиксирую их до оценки второй.
Прямой прогноз оказался точнее рекурсивного, но правило превышения температуры пропустило
скрытую аварию. Хорошая ошибка прогноза сама по себе не делает автоотключение надёжным.
